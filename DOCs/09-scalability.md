# 09. Scalability and capacity thinking

Практическое приложение [ADR-0010](adr/0010-scalability-model.md).

## Единица изоляции

**Endpoint** (TCP host:port) — единица планирования:

- свой strand;
- своя write queue;
- свой reconnect state machine;
- падение/тормоза endpoint A не останавливают endpoint B.

Устройства (`unit id`) на одном TCP — **не** изолированы друг от друга на транспорте (ограничение Modbus TCP). Их разделяют только приоритеты очереди.

## Как расти числом тегов

1. Карта должна собирать **непрерывные блоки** регистров (`pollGroups.blocks`).
2. Translator нарезает блок на теги без лишних PDU.
3. TagStore хранит теги, не «сырой образ всего устройства» как единственный API (сырой буфер — деталь adapter/core poller).

## Как расти числом клиентов SCADA

- Один TagStore, много UA MonitoredItems.
- Не плодить опрос поля «на клиента».
- Publishing interval ≤ ожидания HMI, но sampling не чаще осмысленного poll.

## Когда делить процессы

Делить на несколько процессов/хостов, если:

- упираемся в CPU одного reactor’а при приемлемых блоках;
- нужна изоляция контуров безопасности (разные зоны);
- холодный historian начинает мешать latency.

До этого — один процесс, чёткие порты (проще ops).

## Capacity checklist для проекта карты

- [ ] Fast-группы не содержат редкие статусы.
- [ ] Нет read-per-tag там, где возможен блок.
- [ ] Writable теги осознанны и малочисленны.
- [ ] Timeouts согласованы с period (timeout < period для single-inflight).
- [ ] `opc-map doctor` по проекту не орёт о пересечениях и дырах.
