# 01. Обзор: промышленный OPC UA-сервер для SCADA

## Назначение

`OPC_SERVER` — промышленный программный шлюз между полевым уровнем (устройства с **Modbus TCP/UDP**) и верхним уровнем (**SCADA / HMI / MES**) через **OPC UA**.

Сервер решает четыре прикладные задачи:

| Задача | Суть |
|--------|------|
| **Диспетчеризация** | Планирование и приоритизация опросов, очереди записи вниз к устройствам, согласование циклов |
| **Отладка** | Трассировка кадров Modbus, сессий UA, live-просмотр тегов, replay истории |
| **Транслирование** | Преобразование протоколов и семантики: регистры Modbus ↔ теги OPC UA (типы, scale/offset, единицы, имена) |
| **Накопление** | Краткосрочный и долгосрочный буфер значений с метками времени и качеством для анализа и replay |

Поток данных (упрощённо):

```text
Полевые устройства (Modbus)
        ↓ опрос / запись
   OPC_SERVER (TagStore + Translator + Dispatcher)
        ↓ OPC UA (Read / Write / Subscriptions)
   SCADA / HMI / клиенты отладки
```

## Роли системы

- **Southbound (юг):** клиент Modbus TCP (приоритет); UDP — последующий этап.
- **Core:** хранилище тегов (`TagStore`), диспетчер опросов, транслятор типов/семантики, историк.
- **Northbound (север):** **OPC UA Server** — основной интерфейс для SCADA.
- **Engineering:** проекты карт Modbus (`*.modbusproj.json`) и инструмент `opc-map` для удобной разметки.

## Граница: OPC UA и OPC Classic / DA

| Стек | Статус в проекте |
|------|------------------|
| **OPC UA** | **Основной и единственный реализуемый** northbound на текущем этапе |
| **OPC Classic / DA** (COM/DCOM) | **Вне объёма реализации.** Документируется только как граница совместимости |
| Будущий адаптер Classic/DA | Возможен позже как отдельный шлюз или мост к UA (не часть ядра) |

Почему UA:

- транспорт TCP (типично порт `4840`), без зависимости от DCOM;
- встроенная модель безопасности (политики Sign / Sign&Encrypt, сертификаты);
- единая информационная модель, Subscriptions / MonitoredItems;
- поддержка современными SCADA и кроссплатформенность (Linux / Windows).

Classic/DA остаётся в «карте границ» для объектов, где SCADA ещё требует DA: подключение через внешний UA↔DA мост или будущий опциональный модуль, **не** через смешение протоколов в ядре.

## Функциональные требования (верхний уровень)

1. Загрузка и валидация **проекта** карты Modbus (сеть, устройства, регистры, теги, маппинг в UA).
2. Циклический опрос Holding/Input Registers и Coils/Discrete Inputs по группам с заданным периодом.
3. Публикация актуальных значений в OPC UA с `DataValue` (значение, статус/качество, временные метки).
4. Запись из SCADA в разрешённые теги → очередь write-down в Modbus.
5. Отладочные каналы: логи кадров, метрики latency, watchlist тегов.
6. Накопление истории (hot buffer → cold storage) с политикой retention и возможностью replay.

## Нефункциональные требования

| Область | Требование |
|---------|------------|
| **Детерминизм опроса** | Предсказуемые периоды групп; изоляция медленных устройств от fast-групп |
| **QoS тегов** | Качество отражает доступность устройства, таймаут, CRC/исключение Modbus, устаревание данных |
| **Безопасность UA** | Поддержка политик None (только lab), Sign, Sign&Encrypt; управление сертификатами |
| **Наблюдаемость** | Структурированные логи, метрики (poll RTT, drop rate, UA sessions), трассировка |
| **Удобство инженерии** | Проекты карт с именами, группами, профилями устройств, схемой и CLI-валидацией |
| **Переносимость** | Linux и Windows; C++23; без привязки ядра к COM |

## Вне объёма текущего этапа документации → реализации

- Полноценный OPC DA / Classic server или встроенный DCOM-стек.
- Произвольные полевые протоколы кроме Modbus (IEC 60870, DNP3 и т.д.) — только как возможное расширение Translator.
- Полноценный GUI SCADA; допускается будущий TUI/UI редактор карт.
